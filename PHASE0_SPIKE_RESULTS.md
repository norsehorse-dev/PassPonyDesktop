# PassPony Desktop — Phase 0 spike results

**Verdict: rpgp is the pass/OpenPGP backend. Build on it.**

The spike from `PHASE0_FINDINGS.md` ran against real, freshly generated keys and
real gpg-produced pass entries. Every decision-critical check passed. Below is
exactly what was tested, what passed, what could not be tested here and why, and
the two implementation notes the real backend must carry.

## Setup

- rpgp = the `pgp` crate `0.20.0`, rand `0.8` (matching rpgp's own trait
  versions). Rust 1.95.
- gpg `2.4.4` generated three keys, each with an encryption subkey, and wrote
  pass-style entries (binary `.gpg`, one recipient from `.gpg-id`):
  - **RSA-3072** (primary + RSA encryption subkey)
  - **Ed25519 / Cv25519** (the modern gpg default)
  - **Ed25519 / Cv25519 with a passphrase** on the secret key
- A throwaway crate implemented `pass_core`'s `CryptoBackend` shape over rpgp:
  `decrypt(ciphertext) -> plaintext` and `encrypt(plaintext, recipient)`, plus
  the recipient-resolution rule ported from `PgpEngine.resolve()`.

## Results

Every line is a real assertion the spike made and passed.

| Check | RSA | Cv25519 | Locked | v6 |
|---|---|---|---|---|
| Decrypt a **real gpg** pass entry | PASS | PASS | PASS (unlock w/ passphrase) | n/a |
| rpgp encrypt then rpgp decrypt | PASS | PASS | PASS | PASS |
| **Real gpg decrypts rpgp's output** | PASS | PASS | PASS | not here (see below) |
| Resolve full fingerprint | PASS | PASS | PASS | PASS |
| Resolve lowercase + `0x` prefix | PASS | PASS | PASS | — |
| Resolve 16-hex key-id suffix | PASS | PASS | PASS | — |
| Reject an unrelated id | PASS | PASS | PASS | — |

- **Interop is bidirectional** for RSA and Cv25519: rpgp opens what gpg wrote,
  and gpg opens what rpgp wrote. That is the interop floor a `pass` desktop
  lives or dies on, and it holds.
- **Passphrase-locked secret keys** unlock and decrypt, and gpg reads the entry
  the locked-key backend produced.
- **RSA decrypt works in software** in rpgp. Worth calling out: iOS's
  NorseHorsePGPCore deliberately has no software RSA (smartcard-only). rpgp
  gives the desktop something the iOS app cannot do today, opening ordinary
  RSA `pass` stores.
- **v6 / RFC 9580** (Ed25519 primary + X25519 encryption subkey, generated by
  rpgp since gpg 2.4 cannot): encrypt and decrypt round-trip cleanly through the
  same backend seam.

## What could not be tested on this box, and why

Neither is a gap in rpgp; both are environment limits, and both are easy to
close on a machine that has the tools.

1. **gpg decrypting an rpgp v6 message.** gpg 2.4.4 predates RFC 9580 key
   support; v6 landed in the gpg 2.6 line. The v6 round-trip was proven
   rpgp-to-rpgp. Cross-decrypt against gpg 2.6 (or `sq`) is a five-minute check
   on an up-to-date box and should go in CI there.
2. **Cross-device against actual PGPony phone fixtures.** The spike used gpg as
   the interop peer, which is the more important real-world case for `pass`
   (existing stores are gpg stores). Round-tripping the phones' own shared
   ciphertext fixtures is worth adding when the app is scaffolded, against the
   fixtures in the PassPonyAndroid / PassPonyCore trees.

## Two implementation notes the real backend must carry

These are the only behaviours the spike had to get right beyond the obvious, and
they belong in the backend from day one:

1. **Opt into GnuPG's non-standard AEAD packet (tag 20).** Modern gpg emits it
   whenever the recipient key advertises AEAD, which every key gpg 2.4 generates
   now does. rpgp reads it, but only when asked. The decrypt path must go
   through `TheRing` with
   `DecryptionOptions::new().enable_gnupg_aead()`, not the bare
   `Message::decrypt`, or real-world entries fail with "GnuPG's AEAD packet
   (type 20) is non-standard." Consider also `enable_legacy()` so very old
   non-MDC `SymEncryptedData` entries still open, weighed against the MDC
   security caveat (a settings toggle, defaulting off, is the likely answer).
2. **Pick the SEIPD version by recipient.** The spike encrypted with SEIPD v1 +
   AES256, which is what a v4 gpg recipient expects, and rpgp accepted it even
   for the v6 key. Best practice is SEIPD v2 for a v6-only recipient set; the
   backend should choose per the recipients resolved from `.gpg-id` rather than
   hard-coding v1. Not a blocker, a polish item.

## Recommendation, now evidence-backed

Scaffold the app on rpgp. It covers the whole key-type matrix `pass` needs,
interoperates both directions with real gpg stores, handles passphrase-locked
keys and v6, and keeps the pure-Rust single-binary property that is the reason
this app is native Rust. Keep sequoia as the named fallback only if a concrete
real-world key surfaces that rpgp mishandles; nothing in this spike did. Keep
gpg shell-out for the deferred smartcard story.

The recipient-resolution rule and the two notes above carry straight into the
first real `PgpBackend` in the scaffold.
